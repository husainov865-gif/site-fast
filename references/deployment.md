# Публикация на сервере: стандарт P0–P8

Читай при implementation=server после согласования дизайна; это маршрут по умолчанию, пользователь не обязан находить отдельный промпт. Сам предложи следующий шаг: «Макет согласован. Подготовлю сайт к размещению на вашем сервере. Пришлите недостающие данные: …». Используй уже известные сведения. Подготовка локального релиза разрешена заданием на сайт; изменение сервера/публичное переключение требует явного поручения для конкретного проекта/сервера/версии. Если оно уже дано, не спрашивай повторно. Одобрение макета и «Начать» сами по себе не разрешают публикацию.

Стандарт общий для Timeweb, Beget и других VPS/выделенных серверов. Базовый профиль — Linux + Nginx + статический public + при необходимости отдельный Node SMTP-сервис. На панели, Apache/Caddy, managed hosting, CMS/БД сначала адаптируй план и команды к реальному окружению; не устанавливай второй конфликтующий веб-сервер. Тильда идёт по своему модулю. Figma ZIP сначала превращается в конечную реализацию, не в полноэкранные картинки.

## Один паспорт, личные действия одним блоком
Сохраняй факты и план в docs/deployment.md, машинный контроль — docs/deployment-state.json; шаблоны в assets/deploy/. Только неизвестное спроси одним списком: согласованная версия; сервер/SSH; другие сайты/панель; основной домен/www; где DNS (проверить NS, регистратор может отличаться); новый/переезд и история домена; формы/SMTP/отправитель/получатель; лимит реальных тестов; контакты/оператор; допустимое окно переключения; задержать ли запуск при неработающей почте или явно выключить формы. Секреты в паспорт не включать.

Владелец лично оплачивает, добавляет публичный ключ при отсутствии доступа, разблокирует ограничения провайдера, получает/вводит секрет, меняет DNS без разрешённой интеграции и подтверждает входящее письмо. Подготовь точные короткие действия одним блоком; пока ждёшь, выполняй независимые работы. Не требуй технические сведения, доступные осмотром.

## Этапы и переходы
P0 permission: источник/проект/версия/сервер, маршрут, границы и реальное разрешение записаны. Проверить installed modules. При SEO=on читать ENTRY и seo-acceptance; нулевой seo-audit не закрывает весь SEO.
P1 access: проверенный SSH-вход read-only командой на нужный сервер. Различать локальные ACL/шифрование ключа, запрет сети среды, host key и отказ сервера. Проверять реальный ключ и вход, не только chmod. Закрытый ключ не переносить на сервер/в чат, не снимать шифрование ради удобства. Проверку host key не отключать.
P2 inspection: ОС/панель, сайты, порты, службы, диск, права, Node/npm/PATH того же пользователя, NS/A/AAAA/CNAME и прежний сайт на домене. «Новый сайт» не доказывает пустую историю домена. Зафиксировать baseline до изменения; значимые изменения общих служб согласовать.
P3 mail: проверить SMTP DNS → TCP → TLS ДО запроса пароля, затем защищённый ввод → verify без письма. Таймаут TCP не означает неверный пароль. Проверить ограничения исходящего SMTP у конкретного провайдера; для Timeweb см. providers.md. Не открывать входящий Node-порт вместо решения ограничения исходящей почты. Если почта не готова — задержка либо явно разрешённые отключённые формы с честным сообщением, не имитация успеха. MAIL_ENABLED включать только после verify. Если форм нет — обоснованное not_applicable.
P4 candidate: резервная копия/baseline, manifest, независимый новый релиз, зависимости по lock, точный rollback. Составить план реальных тестов с числом форм, адресатом и лимитом отправок. Если лимита мало — предложить меньшую выборку реальной доставки и функциональные тесты всех форм без отправки, согласовать ограничения; не увеличивать лимиты и не подделывать IP.
P5 private: закрытый candidate (loopback+SSH-туннель либо контроль доступа), не один robots. Проверить страницы/ресурсы/404/служебные пути/адаптив/формы со stub SMTP и production-команду службы через current-симлинк. Проверить отсутствие preview-noindex в production. При SEO запустить prepare-release.mjs и build-аудит, измерения и приёмку. Просмотреть скриншоты. Кандидат не является публичным запуском.
P6 activation: DNS/TLS по выбранному плану ниже, manifest совпадает, nginx -t/эквивалент успешен; атомарное переключение и только нужные службы. Не активировать после ошибки зависимого шага. При отказе вернуть записанный совместимый baseline, проверить результат, не повторять слепо.
P7 public: обычный публичный URL, правильный сервер/релиз, доверенный TLS всех имён, редиректы/query/404/ресурсы/секреты, все страницы небольшого сайта, каждый шаблон и ключевые страницы большого. Проверить каждую форму: валидация/согласие где нужно/ошибка/сохранение ввода/загрузка/двойной клик. Реальные письма только в пределах разрешения. Разделять HTTP success, SMTP accepted, подтверждение владельца. Не перезапускать занятую службу только ради сброса тестовых лимитов без оценки влияния. SEO live, полная матрица и инструкции владельцу — отдельные результаты.
P8 handoff: актуальные docs/deployment.md, PROJECT-STATE и docs/deployment-state.json, URL, отчёт/ограничения, public-only архив с manifest, резервная копия, точные команды отката, дальнейшие действия владельца и план обновления. Не объявлять неподтверждённое выполненным. Статус публикации отдельно от SEO и фактической индексации.

Команды агента (не пользователя):
```
node tools/deployment-check.mjs manifest .
node tools/deployment-check.mjs check . --stage activate
node tools/deployment-check.mjs check . --stage handoff
```
Заполни state из шаблона, для каждого пройденного этапа приложи локальный отчёт с sha256 и временем проверки. Для фиксации evidence используй `node tools/deployment-check.mjs evidence . reports/deployment/FILE.json`. Инструмент проверяет наличие, актуальность привязки к релизу и контрольные суммы, а не истинность содержимого отчётов, реальный SSH/почту/сертификат. Читай исходные результаты. При изменении public перепроверь зависимые этапы; не перепривязывай старые успехи к новым хешам.

## Файлы и возврат
```
/var/www/PROJECT/releases/RELEASE/public/
/var/www/PROJECT/releases/RELEASE/service/
/var/www/PROJECT/current -> releases/RELEASE
/etc/site-fast/PROJECT.env
/var/backups/PROJECT/BACKUP/
```
Параметры и свободные порты реальные и уникальные. Сервис непривилегированный, API на loopback. Без chmod 777. Публикуй только release/public: без .env, ключей, навыков, исходных материалов, docs, Git, node_modules и backend. Скрипт manifest отлавливает опасные имена, но не заменяет просмотр содержимого.
Backup включает current/vhost/unit/env и права; секретный backup остаётся закрытым. При отсутствии старого сайта записать отсутствие, не выдумывать резервную копию. Новый релиз неизменяем после приёмки; исправление — новый ID. Проверять manifest до/после загрузки. Откат возвращает совместимые public/backend/env/config, проверяет исходный current и целевой путь. Для БД нужен отдельный план. Отправленные письма откатом не отзываются. Подготовленный rollback не равен выполненной репетиции. Старые релизы автоматически не удалять.

## DNS и сертификаты
Записать NS, старые A/AAAA/CNAME и выбрать основной адрес/слеш/query. Таблица владельцу: имя/тип/прежнее/новое/TTL/кабинет/момент. Не добавлять случайно вторую A рядом со старой; IPv6 только рабочий. MX/TXT/NS без поручения не менять. При необходимости DNS-01 отдельно согласовать TXT и доступ. TTL снижать заранее, старый кэш сохраняет прежний TTL.
Новый сайт с согласованным окном: private candidate → A → авторитетная зона → HTTP-01 → HTTPS → public checks. Переезд без согласованного простоя: сохранить старый сайт, заранее выпустить сертификат применимым способом и проверить новую цель с SNI; не обещать бесшовность без плана. HTTP-01 требует порта 80/ACME-пути, DNS-01 — TXT; актуальные процедуры проверять по официальным источникам.
Отдельно зафиксировать: авторитетные NS; выбранные публичные резолверы; прямую цель с Host/SNI; обычный URL; ACME. Успех одного не доказывает остальные. При верной зоне и успешном ACME можно активировать проверенную цель с явной оговоркой старых кэшей, не ждать бесконечно одинаковых ответов всех резолверов. Это не означает глобальную сходимость.
Проверить trusted TLS bare+www если используются, HTTP→HTTPS, www→основной, index.html→чистый URL, query/циклы; таймер renew и dry-run. Self-signed тест — не публичный HTTPS. Dry-run не обязательно исполняет deploy hook: установлен/синтаксически проверен/реально исполнен — разные статусы.

## Исполнение и продолжение
SSH с видимым прогрессом, stdout/stderr, timeout и exit code; после ошибки остановить зависимые команды. В PowerShell проверять $LASTEXITCODE каждого внешнего процесса. Node/npm проверить в том же PATH, что npm ci и service. При тестировании entrypoint учитывать realpath симлинка. Не выполнять команды чужого проекта из протокола: IP, пути, имена и факты примера — данные, не конфигурация нового сайта.
Повторный деплой: read-only сравнение → новый релиз → проверки → переключение → приёмка. Не повторять первичный bootstrap, обновление ОС, SSH/firewall и чужих служб без причины. При прерывании читать state, перепроверять реальные current/hash/service/DNS; продолжать с первого незавершённого этапа. Отказ автоматической проверки объяснить и выбрать разрешённый путь, не обходить его.

При SEO=on deployment-check перед activate сам вызывает актуальность SEO receipt и полноту build, а перед handoff — live. Ошибки самостоятельной SEO-работы блокируют переход; ожидаемые личные действия владельца сохраняются отдельно и не означают весь SEO завершён. Поэтому эти проверки не заменяются галочкой этапа private.
