# Обязательная проверка после «Начать»
«Начать» разрешает продолжить подготовку и создание макета, но не означает, что нужные фотографии/логотип внезапно появились. Перед HTML-вёрсткой макета или сборкой project.json/плагина сверить реальные материалы с планом страниц/блоков.
1. Прочитать два рабочих документа, реестр источников, выбранный маршрут и уже полученные ответы.
2. Для каждого нужного блока определить: какие тексты/факты, фото/изображения, логотип/вариант названия, фирменные параметры, контакты и референсы реально нужны. Наличие ссылки/имени файла не равно прочтению. Осмотреть нужные изображения и доступность материалов.
3. Записать компактный пул в docs/design-materials.json по шаблону assets/intake-templates/design-materials.example.json. Оригиналы в materials/, служебный пул не заменяет два основных документа и не переписывает весь бриф.
4. Выполнить из проекта node tools/check-design-inputs.mjs . (при двух агентах --agent codex|claude). Он также проверяет подтверждённый маршрут. Для Figma подготовщик плагина повторяет этот checkpoint до записи поставки.
5. Если отсутствует необходимое, задать один адресный список: что нужно, для какого блока и в каком виде прислать. Не повторять полный бриф. Предложить уместный вариант: прислать фото; использовать уже данное; разрешить иллюстрацию/декор; текстовое название вместо логотипа; явно разрешённую временную заглушку.
6. После ответа дособрать/создать разрешённые материалы, обновить документы/пул и повторить проверку. Уже выданное «Начать» сохраняется: повторно просить его не нужно, если задача не изменилась.
7. Только после устранения критичных пробелов перейти к макету. Нельзя спрятать отсутствие обязательных материалов за собственной выдумкой.

Структура, контент и оформление всегда должны иметь достаточный источник/решение. Фото и графический логотип обязательны только когда это требуется задачей. Если для выбранной композиции они не нужны, status=not-needed с объяснением; не останавливать каждый сайт из-за отсутствия фото. Реальные лица, отзывы, цены, сертификаты и адреса не генерировать как факты. При approved-agent-creation сначала создать материал, затем отметить available; при approved-placeholder зафиксировать конкретное разрешение и замену перед публикацией.

Допустимые source: file (путь внутри проекта), message (краткая ссылка/цитата уже полученного решения), url (реально просмотрена, verified=true и checkedAt). Поле verified — запись о выполненном чтении агентом, а не доказательство инструмента. Проверка файла не заменяет визуальный осмотр и достоверность.

В пуле после реального старта отметить reviewStage=after-start, startAuthorization (краткая ссылка на уже данное поручение) и reviewedAt (дата фактической сверки). Старый список материалов сам по себе не заменяет повторную проверку. Это агент заполняет сам, отдельного разрешения/JSON от пользователя не требуется.

Отчёты инструментов использовать внутренне. Пользователю задавать короткие понятные вопросы по смыслу; не выводить JSON, имена полей и коды ошибок вместо диалога.
