# Единый маршрут проекта
Сначала module-status и правила modules.md. Без установленных модулей не предлагай платные ветки сам: HTML/сервер. Вопросы о бизнесе и новом/старом сайте остаются обычным брифом. При bundleAware=true либо явном запросе конкретной модульной функции до структуры уточни только неизвестное одним списком:
1. Лендинг, небольшой сайт, большой многостраничный сайт или магазин?
2. Новый сайт, переезд старого или доработка? При переезде нужен старый URL и список сохраняемых адресов/контента.
3. С SEO или без? В режиме комплекта вопрос задаётся даже если seo ещё не установлен. Выбор SEO при его отсутствии требует установки из комплекта; без SEO модуль не нужен.
4. Верстаем на Тильде или публикуем на сервере? В режиме комплекта предложи оба варианта, даже если tilda ещё не установлен. При выборе Тильды без модуля сообщи, что нужно установить site-fast-Tilda; маршрут не заменяй сервером. Для Тильды: после согласованного ZIP сначала направь подключить MCP по приложенной авторской инструкции, затем предложи отдельный промпт вёрстки. Установка модуля не запускает перенос.

Не повторяй ответы из материалов. Сохрани docs/project-route.json:
```json
{"projectType":"small","scenario":"new","seo":false,"implementation":"server","design":"figma"}
```
Значения: projectType=landing|small|large|store; scenario=new|migration|improve; implementation=server|tilda; design=html|figma|export. Для export нужен exportPath к утверждённому ZIP. Поля не заполняй вымышленными ответами. Бесплатный маршрут: html/server/seo=false. При готовом Figma-модуле дизайн по умолчанию figma, без параллельного HTML-макета.

Выполни `node tools/plan-route.mjs . docs/project-route.json`; запиши стадии, блокеры и выбранную платформу в PROJECT-STATE.md. Не меняй маршрут молча. canPrepareDesign разрешает только независимую подготовку дизайна, не перенос/публикацию. При старом TILDA_INSTRUCTION_PENDING предложи обновить модуль; подготовка Figma/handoff может продолжаться. В новом модуле готовый сценарий не означает подключённый MCP. После экспорта используй awaiting_tilda_mcp → awaiting_tilda_transfer; до явного поручения переноса не создавай страницу. Наличие платного архива не означает готовность функции: учитывай status и capabilities.

SEO включено: SEO-карта и design-input до дизайна; после реализации — платформенные проверки. Выключено: без исследований SEO-модуля. Миграция: сначала инвентаризация, адреса, контент и редиректы; большой сайт/магазин: шаблоны страниц, каталог, фильтры, пагинация, CMS и объём функциональности согласуются отдельно. Модули не добавляют оплату/каталог автоматически.

Figma → сервер: после согласования экспортировать текущую версию, проверить ZIP, реализовать конечный HTML/CSS/JS, формы и адаптив; сопоставить с PNG и проверить браузер. Это конечная реализация, не второй дизайн-макет.
Figma → Тильда: сохранить проверенный согласованный ZIP; направить к авторской инструкции подключения MCP и её установочному промпту. После подключения предложить отдельный промпт вёрстки с проектом/ZIP по modules/tilda/ENTRY.md. Только это поручение запускает native Zero Blocks, mapping, readback и проверки. После переноса — просмотр владельцем; публикация отдельно. Не подменять HTML-вставкой или изображением.
При изменении платформы заново проверить адаптив, экспорт, SEO и план публикации; согласование старого маршрута не переносится автоматически.

В режиме комплекта также выясни способ дизайна, если неизвестен: Figma или HTML. При явном выборе Figma без модуля нужен site-fast-Figma. Готовый экспорт — design=export, не заставлять заново создавать макет или устанавливать figma для переноса. При обнаруженном повреждённом figma не переходить молча к HTML; восстановить либо согласовать другой путь.
Планировщик возвращает конкретные module/state/action/message. Блокер одной функции не запрещает независимую подготовку материалов; SEO-блокер должен быть решён до SEO-зависимой структуры/дизайна. canExecuteRequestedRoute=false не означает запрет всего диалога.

## Платформа до подготовки Figma
При создании дизайна нашим плагином неизвестную implementation нужно уточнить ДО project.json. Не считать server молчаливым значением. Смысловой макет/Auto Layout и формат ZIP общие, но у Тильды есть ограничения нативных элементов, глубины групп, эффектов, шрифтов и breakpoint mapping. Поэтому платформа влияет на подготовку, хотя второй интерфейс плагина и отдельный экспорт не нужны.
Для явного перехода существующего HTML→Figma используй module/figma/references/html-to-figma.md. Не переписывай исходный HTML и не подключай официальный Figma MCP. После подготовки файлов требуется ручной запуск плагина пользователем, а не доступ агента к Figma.

## Опросник должен быть завершён до предложения «Начать»
После материалов и референсов задай одним сообщением только неизвестное:
1. Какой объём: лендинг / небольшой сайт / большой многостраничный / магазин?
2. Новый сайт / замена-переезд старого / доработка?
3. В режиме комплекта: SEO нужно или нет?
4. В режиме комплекта: конечная реализация на Тильде или своём сервере?
5. Если не сказано: дизайн в Figma или HTML? При готовом экспорте — сразу export.
Не пропускай пункты3–4 из-за наличия материалов/логотипа/референса: они определяют маршрут. Из материалов или явного первого поручения ответ уже может быть известен — повторно его не спрашивать. Если всё известно, кратко перечислить выбранный путь.
В чистой бесплатной установке без следов комплекта платные функции сам не рекламируй: выясни тип/объём/сценарий, зафиксируй HTML/сервер/без SEO как бесплатный маршрут. Явный запрос другой функции обрабатывается по modules.md.

В docs/project-route.json добавь confirmedFields и decisionNotes, с кратким указанием реального ответа/источника для каждого подтверждённого поля. Для режима комплекта нужны projectType/scenario/seo/implementation/design; для бесплатного — projectType/scenario, остальные значения зафиксированы бесплатным профилем. Не заполнять подтверждения по выдуманным предположениям. Если ответы уже были в чате/документах, перенести их с источником без повторной анкеты.
Команда перед приглашением «Начать»: node tools/plan-route.mjs . docs/project-route.json --for-design. Без подтверждений canPrepareDesign=false; предложение начинать рано. После «Начать» всё равно выполнить design-readiness.md и проверить реальные материалы.

Пример дополнения к маршруту:
confirmedFields: ["projectType","scenario","seo","implementation","design"]
decisionNotes: {"projectType":"Пользователь: лендинг","scenario":"Пользователь: новый","seo":"Пользователь: без SEO","implementation":"Пользователь: Тильда","design":"Пользователь: Figma"}
